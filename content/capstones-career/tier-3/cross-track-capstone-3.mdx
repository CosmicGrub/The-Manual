## The assignment: one project, stated as a brief

Build **TrailLink**: a hiking-trail network stored as a weighted graph, with a REST API that computes real shortest routes between trailheads, a frontend that lets a person request and see a route, and a logbook that remembers hikes across restarts. Here's the floor — everyone building this has to clear it:

- The trail network is a weighted, undirected graph: `trailheads` are nodes, `segments` are edges between two trailheads, and every segment carries both a `distance_km` and an `elevation_gain_m`.
- `POST /trailheads` and `POST /segments` let you build the network; `GET /trailheads` lists what exists.
- `GET /route?from=<id>&to=<id>&optimize=distance|elevation` returns the best path between two trailheads as an ordered list of trailhead names, plus the total distance and total elevation gain of that path — computed by **actually running a weighted shortest-path algorithm**, not by hardcoding a few known routes.
- `optimize=distance` and `optimize=elevation` must return genuinely different paths over the same graph when the data calls for it, because they're optimizing two different edge weights on the same edges. If your implementation always returns the same path regardless of `optimize`, you haven't built the thing yet — you've built a cache of one path.
- `POST /hikes` logs a completed hike (user, trailhead sequence, date) against real data; `GET /users/<id>/stats` returns that user's total distance hiked, total elevation gained, and single longest hike, computed from the logged hikes.
- All of it survives a process restart — a relational database, not an in-memory dict.
- A frontend page lets a person pick a start trailhead, an end trailhead, and an optimize mode, calls `GET /route`, and renders the result; a "log this hike" action calls `POST /hikes` for the route just shown.

That `optimize` parameter is the real design decision in this project, the same way base62 encoding was the real design decision in Capstone #2. It forces you to actually implement Dijkstra's algorithm (or an equivalent priority-queue-based shortest path) over an adjacency list you build from the `segments` table — twice, with two different weight functions — instead of writing a `/route` endpoint that looks right on one test case and falls over on the second.

## The floor, as acceptance tests

```python
# test_floor_api.py — you did not write this file, you make it pass
import requests

BASE = "http://localhost:5000"

def seed_diamond_graph():
    """A -> B -> D is short but steep. A -> C -> D is longer but flat."""
    ids = {}
    for name in ["A", "B", "C", "D"]:
        r = requests.post(f"{BASE}/trailheads", json={"name": name})
        ids[name] = r.json()["id"]
    requests.post(f"{BASE}/segments", json={
        "from_id": ids["A"], "to_id": ids["B"], "distance_km": 2, "elevation_gain_m": 400})
    requests.post(f"{BASE}/segments", json={
        "from_id": ids["B"], "to_id": ids["D"], "distance_km": 2, "elevation_gain_m": 400})
    requests.post(f"{BASE}/segments", json={
        "from_id": ids["A"], "to_id": ids["C"], "distance_km": 5, "elevation_gain_m": 50})
    requests.post(f"{BASE}/segments", json={
        "from_id": ids["C"], "to_id": ids["D"], "distance_km": 5, "elevation_gain_m": 50})
    return ids

def test_shortest_by_distance_takes_the_steep_short_path():
    ids = seed_diamond_graph()
    r = requests.get(f"{BASE}/route", params={"from": ids["A"], "to": ids["D"], "optimize": "distance"})
    body = r.json()
    assert body["path"] == ["A", "B", "D"]
    assert body["total_distance_km"] == 4

def test_shortest_by_elevation_takes_the_flat_long_path():
    ids = seed_diamond_graph()
    r = requests.get(f"{BASE}/route", params={"from": ids["A"], "to": ids["D"], "optimize": "elevation"})
    body = r.json()
    assert body["path"] == ["A", "C", "D"]
    assert body["total_elevation_gain_m"] == 100

def test_unreachable_trailhead_is_404():
    ids = seed_diamond_graph()
    island_id = requests.post(f"{BASE}/trailheads", json={"name": "Island"}).json()["id"]
    r = requests.get(f"{BASE}/route", params={"from": ids["A"], "to": island_id, "optimize": "distance"})
    assert r.status_code == 404

def test_logging_a_hike_updates_user_stats():
    seed_diamond_graph()
    requests.post(f"{BASE}/hikes", json={
        "user_id": 1, "path": ["A", "B", "D"], "date": "2026-09-01"})
    stats = requests.get(f"{BASE}/users/1/stats").json()
    assert stats["total_distance_km"] == 4
    assert stats["longest_hike_km"] == 4

def test_persists_across_restart():
    ids = seed_diamond_graph()
    # -- restart your server process here, by hand, before re-running this test --
    r = requests.get(f"{BASE}/route", params={"from": ids["A"], "to": ids["D"], "optimize": "distance"})
    assert r.json()["path"] == ["A", "B", "D"]
```

Six tests, zero implementation. The two shortest-path tests are the load-bearing pair: they run against the exact same graph, so the only way both pass is if your route computation genuinely runs twice with two different edge weights — there is no shortcut that makes both green by accident.

## The schema and the layering

The persistence layer is three tables, built with the normalization and foreign-key discipline from Language Mastery's Advanced SQL and Data Modeling module — don't re-derive third normal form from scratch here, apply it:

```sql
CREATE TABLE trailheads (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE segments (
    id               INTEGER PRIMARY KEY,
    from_id          INTEGER NOT NULL REFERENCES trailheads(id),
    to_id            INTEGER NOT NULL REFERENCES trailheads(id),
    distance_km      REAL NOT NULL,
    elevation_gain_m REAL NOT NULL,
    closed           INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE hikes (
    id      INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    path    TEXT NOT NULL,   -- JSON array of trailhead names, in order
    date    TEXT NOT NULL
);
```

Software Engineering's Clean Architecture and Hexagonal Design module already gave you the reason to keep these concerns in separate files instead of one `app.py`: a `routes` layer that only parses HTTP and calls into a `graph` module, a `graph` module that only knows about nodes/edges/Dijkstra and nothing about HTTP or SQL, and a `store` module that only knows SQL. The test for whether you actually did this: can you unit-test `graph.shortest_path(adjacency, start, end, weight="elevation")` with a plain Python dict and zero running server? If you can't, HTTP and your algorithm are tangled together — exactly the coupling that module exists to prevent. CS Foundations' Multi-File Project Architecture module covers the file-layout side of the same decision; reuse it instead of guessing at a layout.

## Testing it end to end, not just the API in isolation

Unit tests on `graph.py` prove the algorithm is right. They don't prove a person can actually click "find route" in a browser and see a path. Software Engineering's End-to-End and Contract Testing module already covers the Playwright setup you need — apply it here instead of improvising your own:

```python
# test_e2e_route.py
from playwright.sync_api import sync_playwright

def test_user_can_request_and_see_a_route():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page()
        page.goto("http://localhost:3000")
        page.select_option("#from-trailhead", label="A")
        page.select_option("#to-trailhead", label="D")
        page.select_option("#optimize", label="distance")
        page.click("#find-route")
        page.wait_for_selector(".route-result")
        assert "A" in page.inner_text(".route-result")
        assert "4" in page.inner_text(".route-result")  # total_distance_km
        browser.close()
```

This test only passes if the frontend, the network call, and the API's Dijkstra implementation are all correct and actually wired together — a gap a frontend-only or backend-only test suite can't see.

## The bug you will plausibly hit

Say you add an in-memory cache so `/route` doesn't rebuild the adjacency list from the database on every single request — a reasonable optimization once the network has a few hundred segments:

```python
_graph_cache = None

def get_graph():
    global _graph_cache
    if _graph_cache is None:
        _graph_cache = build_adjacency_list_from_db()
    return _graph_cache
```

You add a new, much shorter segment with `POST /segments`, then call `GET /route` between the two trailheads it connects — and it still returns the old, longer path. Every single time, not occasionally.

**That "every single time" is the diagnostic clue.** Capstone #2's race condition failed intermittently, because two threads were genuinely racing for the same resource. This bug is deterministic: it fails 10 times out of 10, the same way, which rules out concurrency as the cause before you've even opened a debugger. A bug that's wrong on *every* run is a logic error, not a timing error — go looking in whatever code path runs identically each time, not in thread interleaving.

Trace it: `get_graph()` builds `_graph_cache` once, on the very first call, and after that every request — including the one right after your `POST /segments` — reads that same stale object back. The write path and the read path never talk to each other.

This is a real, named system-design problem, not a one-off typo: **cache invalidation**, specifically a cache with no eviction or refresh trigger tied to the writes that should invalidate it. Two real fixes, with real tradeoffs:

| Approach | Mechanism | Cost |
|---|---|---|
| Invalidate on write | `POST /segments` sets `_graph_cache = None` right after the insert | Simple and correct, but every write pays for a full rebuild on the very next read |
| Cache-aside with a version counter | Store a `graph_version` row in the DB; the cache remembers which version it was built from and rebuilds when they diverge | Survives multiple server processes sharing one database, which a plain in-process global does not |

Pick the invalidate-on-write version first — it's the one that actually matches a single-process deploy like the Fly.io target above — and confirm the earlier test passes again after a `POST /segments`, with no process restart in between.

## Exercise: trail closures and a connectivity check

Add `PATCH /segments/<id>` to mark a segment `closed: true`, and make `/route` ignore closed segments when computing a path. Then add `GET /trailheads/<id>/reachable`, which must answer a different question: starting from this trailhead, with closed segments removed from the graph, which other trailheads can still be reached at all? This is a different algorithm from Dijkstra — you don't need shortest distance here, you need every reachable node, which is a plain graph traversal.

```python
def test_closed_segment_disconnects_an_island_trailhead():
    ids = seed_diamond_graph()  # A-B-D and A-C-D as before
    e_id = requests.post(f"{BASE}/trailheads", json={"name": "E"}).json()["id"]
    seg = requests.post(f"{BASE}/segments", json={
        "from_id": ids["D"], "to_id": e_id, "distance_km": 1, "elevation_gain_m": 10}).json()
    requests.patch(f"{BASE}/segments/{seg['id']}", json={"closed": True})

    reachable = requests.get(f"{BASE}/trailheads/{ids['A']}/reachable").json()["reachable"]
    assert "E" not in reachable
    assert "D" in reachable  # A to D still has two open paths
```

**Hint, not a solution:** CS Foundations' Graph Theory Fundamentals module already covered the two standard traversals — breadth-first and depth-first — that visit every node reachable from a start point. Either one answers "what's reachable" correctly; Dijkstra's priority queue is solving a different question ("what's *shortest*") and is the wrong tool here even though it's sitting right next to this code in your `graph.py`. Filter closed segments out of the adjacency list before you traverse, not after.
