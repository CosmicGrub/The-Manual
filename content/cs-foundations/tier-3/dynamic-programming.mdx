Every dynamic programming problem is a recursion you already know how to write, wearing a disguise. You break the problem into smaller versions of itself — exactly like you did with factorial and Fibonacci back in Tier 1 — except this time the recursion tree branches into the *same* subproblem over and over, dozens or millions of times, and the entire discipline of DP is noticing that and refusing to redo the work twice. That's it. There's no new kind of thinking here beyond recursion plus one extra habit: cache what you've already computed, or build it up from the bottom so you never ask for something you haven't already got.

This module is deliberately less hand-held than Tier 1-2 material. You'll be given the recurrence and the real problem, and expected to wrestle with the indexing, the base cases, and the off-by-ones yourself before checking a reference — because that wrestling *is* the skill. DP bugs are almost never conceptual; they're a `<=` that should've been `<`, or a loop that runs forward when it needed to run backward. Getting fast at spotting those is the actual outcome of this lesson.

## What you'll leave this lesson knowing

- The difference between memoization (top-down: recursion + a cache) and tabulation (bottom-up: an iteratively-filled table), and a real sense of when each is more natural
- How to derive and implement the classic recurrences for 0/1 knapsack, longest common subsequence, and edit distance — from scratch, verified against known answers — including reconstructing the actual solution (which items, which subsequence, which edits), not just the optimal number
- The two-question checklist for recognizing whether a new problem is DP-shaped at all (optimal substructure + overlapping subproblems), and practice applying it to problems you haven't seen worked out
- Why a single off-by-one or a wrong loop direction in DP code can silently change *which* problem you're solving (not just crash) — and how to catch that in review

## Do this

1. **Rediscover why naive recursion falls over — with a stopwatch, not just a claim.** Write the textbook recursive Fibonacci:
   ```python
   def fib_naive(n):
       if n < 2:
           return n
       return fib_naive(n - 1) + fib_naive(n - 2)
   ```
   Time `fib_naive(30)` and `fib_naive(35)` with `time.perf_counter()`. On a typical laptop, `fib(30)` takes roughly a tenth of a second and `fib(35)` takes over a second — for a function that's supposedly just adding two numbers. The reason is the recursion tree: `fib_naive(35)` calls `fib_naive(33)` and `fib_naive(32)`, but `fib_naive(33)` *also* calls `fib_naive(32)` — the same subproblem gets recomputed from scratch, and that duplication compounds exponentially. Confirm this isn't just slow but genuinely exponential by timing `fib_naive(20)`, `fib_naive(25)`, `fib_naive(30)` and noticing the roughly ~11x jump per 5 steps (φ^5 ≈ 11.09).

   Now fix it top-down with memoization — cache each `n` the first time you compute it:
   ```python
   import functools

   @functools.lru_cache(maxsize=None)
   def fib_memo(n):
       if n < 2:
           return n
       return fib_memo(n - 1) + fib_memo(n - 2)
   ```
   Time `fib_memo(35)` — it should be instant (microseconds), and `fib_memo(100)` should also return instantly (`354224848179261915075`), which is a good demonstration that the *shape* of the recursion, not the size of `n`, was always the problem. `functools.lru_cache` is memoization: it's still top-down recursion, just with automatic result-caching bolted on. Now write the same thing bottom-up (tabulation) with no recursion at all:
   ```python
   def fib_tab(n):
       if n < 2:
           return n
       table = [0, 1]
       for i in range(2, n + 1):
           table.append(table[i - 1] + table[i - 2])
       return table[n]
   ```
   Both `fib_memo` and `fib_tab` are O(n) — there are only `n + 1` unique subproblems (`fib(0)` through `fib(n)`), and each one now gets computed exactly once. That's the whole idea of DP in one sentence: **turn an exponential number of redundant calls into a linear number of unique states.**

2. **0/1 Knapsack — implement it yourself before reading further.** You have items with weights and values and a knapsack with a weight capacity; you can take each item at most once (hence "0/1" — you either take it or you don't); maximize total value without exceeding capacity.

   Stop and actually attempt this before scrolling past the reference below. Start with plain recursion — for each item, you either skip it or take it (if it fits) — then notice which `(item_index, remaining_capacity)` pairs get asked for more than once, and cache on that pair. Give yourself 20-30 minutes with this input before checking your answer:
   ```python
   weights = [1, 3, 4, 5]
   values  = [1, 4, 5, 7]
   capacity = 7
   # expected best value: 9
   ```

   Here's one correct path, built in three stages so you can see exactly where the speedup comes from. First, the naive recursion (exponential — don't run this on large inputs):
   ```python
   def knapsack_rec(weights, values, i, capacity):
       if i == len(weights) or capacity == 0:
           return 0
       if weights[i] > capacity:
           return knapsack_rec(weights, values, i + 1, capacity)
       skip = knapsack_rec(weights, values, i + 1, capacity)
       take = values[i] + knapsack_rec(weights, values, i + 1, capacity - weights[i])
       return max(skip, take)
   ```
   Second, memoize on the two things that vary — `(i, capacity)` — since that pair fully determines the answer to a subcall regardless of how you got there:
   ```python
   @functools.lru_cache(maxsize=None)
   def knapsack_memo(i, capacity):
       if i == len(weights) or capacity == 0:
           return 0
       if weights[i] > capacity:
           return knapsack_memo(i + 1, capacity)
       skip = knapsack_memo(i + 1, capacity)
       take = values[i] + knapsack_memo(i + 1, capacity - weights[i])
       return max(skip, take)

   print(knapsack_memo(0, capacity))   # 9
   ```
   Third, tabulation — build a 2D table `dp[i][c]` = best value using the first `i` items with capacity `c`, filled bottom-up, and reconstruct *which* items were chosen by walking back through the table (if `dp[i][c] != dp[i-1][c]`, item `i-1` was taken):
   ```python
   def knapsack_tabulated(weights, values, capacity):
       n = len(weights)
       dp = [[0] * (capacity + 1) for _ in range(n + 1)]
       for i in range(1, n + 1):
           w, v = weights[i - 1], values[i - 1]
           for c in range(capacity + 1):
               dp[i][c] = dp[i - 1][c]                    # don't take item i-1
               if w <= c:
                   dp[i][c] = max(dp[i][c], dp[i - 1][c - w] + v)   # take it

       # reconstruct which items were chosen
       chosen = []
       c = capacity
       for i in range(n, 0, -1):
           if dp[i][c] != dp[i - 1][c]:
               chosen.append(i - 1)
               c -= weights[i - 1]
       chosen.reverse()
       return dp[n][capacity], chosen

   best, chosen = knapsack_tabulated(weights, values, capacity)
   print(best, chosen)
   # 9 [1, 2]  -> items at index 1 and 2 (weight 3+value 4, weight 4+value 5) = weight 7, value 9
   ```
   Confirm you get `9` and `[1, 2]` from all three versions before moving on. Notice the table is `(n+1) x (capacity+1)` — that "+1" row/column for the empty-prefix/zero-capacity base case is the single most common off-by-one source in DP code, so get used to reasoning about *why* it's there instead of memorizing it.

3. **Longest Common Subsequence (LCS) — same three-stage pattern, applied to strings.** A subsequence doesn't have to be contiguous, just in order. The recurrence: if the last characters of both strings match, they're part of the LCS and you recurse on both strings minus their last character, plus 1; if they don't match, the LCS is the better of dropping the last character of *either* string.

   Write the recursive version yourself first from that description alone (don't look at the tabulated version below yet). Then build the bottom-up table and reconstruct the actual subsequence (not just its length) by walking back from the bottom-right corner:
   ```python
   def lcs(a, b):
       n, m = len(a), len(b)
       dp = [[0] * (m + 1) for _ in range(n + 1)]
       for i in range(1, n + 1):
           for j in range(1, m + 1):
               if a[i - 1] == b[j - 1]:
                   dp[i][j] = dp[i - 1][j - 1] + 1
               else:
                   dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])

       # reconstruct the actual subsequence, walking back from dp[n][m]
       i, j = n, m
       seq = []
       while i > 0 and j > 0:
           if a[i - 1] == b[j - 1]:
               seq.append(a[i - 1])
               i -= 1
               j -= 1
           elif dp[i - 1][j] >= dp[i][j - 1]:
               i -= 1
           else:
               j -= 1
       seq.reverse()
       return dp[n][m], "".join(seq)

   print(lcs("ABCBDAB", "BDCABA"))   # (4, 'BCBA')
   ```
   Confirm you get length `4` and the string `'BCBA'` (there are other valid length-4 subsequences of these two strings — `'BDAB'` is also correct if your reconstruction breaks ties the other way; the length must be exactly 4 either way). LCS is the base pattern behind `diff` tools and version-control merge algorithms — the next time `git diff` shows you a clean set of added/removed lines instead of "everything changed," this is roughly the algorithm underneath.

4. **Edit distance (Levenshtein) — the same table shape, three operations instead of two.** You're turning string `a` into string `b` with insertions, deletions, and substitutions, each costing 1; minimize the total. The recurrence: if the current characters match, no cost, move both pointers back; if they don't, pay 1 and take the best of the three operations (delete from `a`, insert into `a` to match `b`, or substitute).
   ```python
   def edit_distance(a, b):
       n, m = len(a), len(b)
       dp = [[0] * (m + 1) for _ in range(n + 1)]
       for i in range(n + 1):
           dp[i][0] = i       # deleting all of a's first i chars
       for j in range(m + 1):
           dp[0][j] = j       # inserting all of b's first j chars

       for i in range(1, n + 1):
           for j in range(1, m + 1):
               if a[i - 1] == b[j - 1]:
                   dp[i][j] = dp[i - 1][j - 1]
               else:
                   dp[i][j] = 1 + min(
                       dp[i - 1][j],       # delete a[i-1]
                       dp[i][j - 1],       # insert b[j-1]
                       dp[i - 1][j - 1],   # substitute
                   )
       return dp[n][m]

   print(edit_distance("kitten", "sitting"))   # 3
   ```
   Confirm you get `3` (k→s, e→i, insert g). Before running it, work out by hand *why* the base cases are `dp[i][0] = i` and `dp[0][j] = j` — what real-world edit sequence does `dp[3][0] = 3` correspond to? As a stretch (optional but worth doing once): modify the function to also return the actual sequence of operations, not just the count, by tracking which of the three branches was taken at each cell during the fill and walking that trail back from `dp[n][m]`, the same reconstruction idea as step 3.

5. **Recognize DP without being told it's DP.** A problem is DP-shaped when both of these hold:
   - **Optimal substructure** — an optimal solution to the whole problem is built from optimal solutions to smaller subproblems of the *same* kind (not just "smaller" — genuinely the same problem, smaller).
   - **Overlapping subproblems** — a plain recursive solution would ask for the same subproblem more than once.

   If a problem has optimal substructure but *no* overlap (each subproblem asked for exactly once), you don't need DP — plain divide-and-conquer, from your previous module, already handles it efficiently.

   Do this one fully yourself, start to finish, with no reference to check against until you've got working code: **Coin Change (minimum coins).** Given a list of coin denominations and a target amount, find the minimum number of coins that sum to exactly that amount (assume unlimited supply of each coin), or determine it's impossible. Work out the recurrence yourself first (hint: `dp[amount]` depends on `dp[amount - coin]` for every coin you could use last), then implement bottom-up. Test it against:
   ```python
   # coins = [1, 3, 4], amount = 6      -> expect 2   (3 + 3)
   # coins = [1, 5, 10, 25], amount = 63 -> expect 6   (25+25+10+1+1+1)
   ```
   If you get stuck, the one-line hint is: `dp[a] = 1 + min(dp[a - c] for c in coins if c <= a)`, with `dp[0] = 0` and everything unreachable marked as infinity. Get your own version passing both cases before moving on.

   Now, without fully implementing them, run the two-question checklist above against these three real problems and write one sentence each stating the state you'd track and the recurrence you'd use:
   - **House Robber** — a row of houses each with some cash; you can't rob two adjacent houses; maximize total take. (State: max take considering houses `0..i`. Recurrence hint: at house `i`, either skip it and take `best(i-1)`, or rob it and take `house[i] + best(i-2)`.)
   - **Longest Increasing Subsequence (LIS)** — the longest subsequence of a list that's strictly increasing, not necessarily contiguous. Try it on `[10, 9, 2, 5, 3, 7, 101, 18]` — the answer is `4` (e.g. `2, 5, 7, 101` or `2, 3, 7, 18`).
   - **Matrix Chain Multiplication** — given a chain of matrices to multiply, choose the parenthesization (order of multiplication) that minimizes total scalar multiplications. (This one's overlapping-subproblems structure is on *intervals* `[i, j]` of the chain rather than a single index — a useful preview of how the state space generalizes beyond "one index" or "two indices.")

   If any of these are unfamiliar shapes, that's the point of "go look it up" at this tier — search for the problem name plus "dynamic programming," read one derivation, then implement it from the recurrence rather than copying a full solution.

6. **Bug hunt: find what's wrong with this "optimized" knapsack before reading the explanation.** A common (bad) shortcut is collapsing the 2D knapsack table into a 1D array to save memory. Here's a version that does that — and it's subtly, dangerously wrong:
   ```python
   def knapsack_broken(weights, values, capacity):
       n = len(weights)
       dp = [0] * (capacity + 1)
       for i in range(n):
           w, v = weights[i], values[i]
           for c in range(w, capacity + 1):        # <-- forward
               dp[c] = max(dp[c], dp[c - w] + v)
       return dp[capacity]
   ```
   Run it against a case where the bug can't hide: a single item with weight `2`, value `3`, and capacity `6`:
   ```python
   print(knapsack_broken([2], [3], 6))   # what does this print?
   ```
   It prints `9` — as if you took the item three times. Correct 0/1 knapsack with one item and capacity `6` should cap out at `3` (you only have one of the item). The bug: collapsing to 1D is a legitimate, standard optimization, but it *requires* iterating the capacity dimension **backward** (`range(capacity, w - 1, -1)`) so that `dp[c - w]` on the right-hand side still refers to *last item's* row, not a value you already overwrote *this* item's pass. Iterating forward lets the same item get "taken" again later in the same inner loop — which silently turns 0/1 knapsack into unbounded knapsack (unlimited copies of each item) without ever raising an error. Fix it yourself (flip the `range()` direction) and re-run both test cases — the single-item case should now correctly return `3`, and the original `weights=[1,3,4,5], values=[1,4,5,7], capacity=7` case should still return `9`. This is exactly the kind of bug this tier's checkpoint bug-hunt kata is built around: code that runs, terminates, and passes some inputs while being flatly wrong on others.
