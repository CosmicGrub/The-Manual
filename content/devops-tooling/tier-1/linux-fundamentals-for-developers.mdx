## Why the filesystem hierarchy matters to you, specifically

Every Linux distribution looks different on the surface — Ubuntu's `apt`, Fedora's `dnf`, Arch's `pacman` — but underneath, almost all of them agree on where things live. That agreement is the **Filesystem Hierarchy Standard (FHS)**. You don't need to memorize the spec. You need to know, on sight, "oh, that's a config file, it's going to be in `/etc`" or "that's a log, check `/var/log`" — because when a production service is broken at 2am, you will not have time to go hunting.

Let's actually look. SSH into any Debian/Ubuntu box (or spin one up — this is exactly the kind of thing to practice on a disposable cloud VM) and run:

```bash
$ ls -la /
total 76
drwxr-xr-x  20 root root  4096 Oct  2 09:14 .
drwxr-xr-x  20 root root  4096 Oct  2 09:14 ..
drwxr-xr-x   2 root root  4096 Sep 10 11:02 bin -> usr/bin
drwxr-xr-x   4 root root  4096 Sep 10 11:03 boot
drwxr-xr-x   4 root root  4096 Oct  1 18:20 etc
drwxr-xr-x   4 root root  4096 Oct  1 08:00 home
drwxr-xr-x  22 root root  4096 Sep 10 11:03 lib -> usr/lib
drwxrwxrwt   8 root root  4096 Oct  3 02:11 tmp
drwxr-xr-x  14 root root  4096 Sep 10 11:03 usr
drwxr-xr-x  13 root root  4096 Oct  1 08:00 var
```

### `/etc` — configuration, no binaries

`/etc` ("editable text configuration," unofficially) holds system-wide config files in plain text. Nothing here is a compiled program.

```bash
$ ls /etc/ssh/
moduli          ssh_config       sshd_config       ssh_host_ed25519_key
ssh_config.d    sshd_config.d    ssh_host_ed25519_key.pub

$ sudo cat /etc/hosts
127.0.0.1   localhost
127.0.1.1   web-01
10.0.0.5    db-primary
```

When you need to change how a service behaves on a running box — the port nginx listens on, which users can SSH in, what DNS resolver is used — you are almost always editing a file under `/etc`. This is also why `/etc` is the first directory you back up or put under version control (`etckeeper` does exactly that) before making changes you might need to undo.

### `/var` — data that changes while the system runs

`/var` is for **var**iable data: logs, caches, spool queues, databases. If `/etc` is "how the system is configured," `/var` is "what the system has been doing."

```bash
$ du -sh /var/log/* | sort -rh | head -5
45M     /var/log/journal
12M     /var/log/nginx
3.2M    /var/log/syslog
1.1M    /var/log/auth.log
220K    /var/log/apt
```

Disk filling up on a server almost always traces back to `/var` — runaway logs, an `apt` cache (`/var/cache/apt/archives`) nobody cleared, or a database under `/var/lib/mysql` that grew past what anyone provisioned for. The first command in any "server is out of disk space" incident is `df -h` followed by `du -sh /var/* | sort -rh`.

### `/usr` — the actual software

`/usr` holds the bulk of installed programs and their supporting files — binaries, libraries, man pages, shared data — whether they shipped with the distro or you installed them with a package manager.

```bash
$ ls /usr/bin | wc -l
1437

$ which python3
/usr/bin/python3

$ ls /usr/local/bin
```

`/usr/local` is the escape hatch: software you compiled and installed yourself, outside the package manager, goes there so it never collides with a package-managed file in `/usr/bin`.

### `/home` — your stuff, and only your stuff

```bash
$ ls -la /home/deploy
drwx------  6 deploy deploy 4096 Oct  2 14:02 .
drwxr-xr-x  2 deploy deploy 4096 Sep 20 09:11 .ssh
-rw-r--r--  1 deploy deploy  807 Sep 20 09:00 .bashrc
```

Every real user gets a subdirectory here, and — note the `drwx------` on the directory itself — by default nobody but that user (and root) can read into it. This is where `~/.ssh/authorized_keys` lives, where personal dotfiles live, where anything scoped to one account belongs.

### `/tmp` — gone by morning, and that's the point

```bash
$ ls -ld /tmp
drwxrwxrwt 8 root root 4096 Oct 3 02:11 /tmp
```

Look at that permission string: `rwxrwxrwt`. Anyone can write here, but the trailing **`t`** is the *sticky bit* — it means you can only delete or rename files you yourself created, even though the directory is world-writable. Most distros wipe `/tmp` on reboot (or via a periodic `systemd-tmpfiles-clean` job), so nothing you care about long-term goes here. It's for lock files, build scratch space, and anything a crashed process should be fine losing.

## Permissions: chmod and chown, down to the bit

Run `ls -l` on any file and you get something like:

```bash
$ ls -l deploy.sh
-rwxr-xr-x 1 carlos devops 312 Oct 2 10:00 deploy.sh
```

Break down `rwxr-xr-x`: it's three groups of three — **owner**, **group**, **other** — each a `read`/`write`/`execute` triplet.

| | r | w | x |
|---|---|---|---|
| value | 4 | 2 | 1 |

Add the values present in each triplet to get one octal digit per group:

- Owner: `rwx` = 4+2+1 = **7**
- Group: `r-x` = 4+0+1 = **5**
- Other: `r-x` = 4+0+1 = **5**

That's where `755` comes from. `chmod 755 deploy.sh` means: the owner can read, write, and execute it; everyone else (group and world) can read and execute it but not modify it. This is the standard permission for a script or binary you want other people to *run* but not *edit*. Compare it to `644` (`rw-r--r--`) — the default for a regular file like a config or a text doc: owner reads/writes, everyone else only reads, nobody executes.

Watch the actual failure mode this prevents:

```bash
$ cat > deploy.sh <<'EOF'
#!/bin/bash
echo "deploying..."
EOF

$ ls -l deploy.sh
-rw-r--r-- 1 carlos devops 32 Oct 2 10:04 deploy.sh

$ ./deploy.sh
bash: ./deploy.sh: Permission denied

$ chmod 755 deploy.sh
$ ls -l deploy.sh
-rwxr-xr-x 1 carlos devops 32 Oct 2 10:04 deploy.sh

$ ./deploy.sh
deploying...
```

`chown` changes *who* owns the file — both user and, optionally, group:

```bash
$ sudo chown www-data:www-data /var/www/html/index.html
$ ls -l /var/www/html/index.html
-rw-r--r-- 1 www-data www-data 612 Oct 2 10:10 index.html
```

This is the real reason you'll touch `chown` in practice: a web server running as the `www-data` user can't write to (and depending on config, sometimes can't even read) files it doesn't own or have group access to. "403 Forbidden" or "502" errors that trace back to a permissions/ownership mismatch between the deploying user and the service user are one of the most common first-week production incidents — know this flow cold.

## Processes and signals: don't reach for `kill -9` first

Every running program is a process with a PID. List them:

```bash
$ ps aux | grep nginx
root       1822  0.0  0.1  55560  3012 ?   Ss   09:00   0:00 nginx: master process
www-data   1823  0.0  0.2  56012  4488 ?   S    09:00   0:01 nginx: worker process
```

Start something in the background and manage it with job control:

```bash
$ sleep 300 &
[1] 28811

$ jobs
[1]+  Running    sleep 300 &

$ kill -l | head -3
1) SIGHUP   2) SIGINT   3) SIGQUIT
```

Now the part people get wrong under pressure: `kill` doesn't mean "force-kill." It *sends a signal*, and which signal matters enormously.

```bash
$ kill 28811          # equivalent to: kill -15 28811, i.e. SIGTERM
```

**SIGTERM (15)** is a *request*: "please shut down." A well-written program installs a handler for it that closes database connections, flushes buffers to disk, finishes an in-flight request, deletes its lock file, then exits. This is how every production process manager — systemd, Docker, Kubernetes — stops a service by default, and why they wait a grace period (systemd's default is 90 seconds, Kubernetes' default `terminationGracePeriodSeconds` is 30) before escalating.

```bash
$ kill -9 28811        # SIGKILL
```

**SIGKILL (9)** cannot be caught, blocked, or ignored — it's handled by the kernel, not the process, and the process dies immediately with no cleanup whatsoever. That sounds convenient when something is hung, but it's exactly what causes corrupted database files, orphaned lock files, half-written log lines, and leaked file descriptors. The rule in any real environment: **always send SIGTERM first, wait, and only escalate to SIGKILL if the process ignores SIGTERM** (check with `ps` — if the PID is still alive after a reasonable wait, *then* `kill -9`). This exact pattern is baked into every real deployment tool for a reason.

## Package management: what `apt` is actually tracking

```bash
$ sudo apt-get install -y htop
Reading package lists... Done
The following NEW packages will be installed:
  htop
0 upgraded, 1 newly installed, 0 to remove, 118 not upgraded.
Need to get 231 kB of archives.
Setting up htop (3.0.5-7) ...
```

A package manager isn't just a downloader. It maintains a *database* of: which packages are installed and at what version, exactly which files on disk belong to which package, and the full dependency graph between packages (what `htop` requires, and what requires `htop`). You can query all three:

```bash
$ dpkg -L htop | head -5
/usr/bin/htop
/usr/share/doc/htop
/usr/share/man/man1/htop.1.gz

$ apt list --installed | grep htop
htop/stable 3.0.5-7 amd64 [installed]
```

That file-ownership tracking is exactly what makes clean removal possible:

```bash
$ sudo apt-get remove htop
Removing htop (3.0.5-7) ...

$ sudo apt-get purge htop     # also removes its config files under /etc
```

`remove` deletes the program but leaves config files behind (in case you reinstall later and want your settings back); `purge` deletes those too. On RHEL/CentOS/Fedora, the equivalent commands are `sudo yum install htop` / `sudo dnf install htop` and `rpm -ql htop` to list owned files — different tool, identical underlying concept: a manifest mapping packages to files, versions, and dependencies, so nothing gets installed or removed by guesswork.

## systemd: starting, stopping, and reading logs for real services

Almost every modern distro uses `systemd` to supervise long-running services. Three commands cover 90% of day-to-day operations:

```bash
$ sudo systemctl status nginx
● nginx.service - A high performance web server
     Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
     Active: active (running) since Thu 2026-10-02 09:00:11 UTC; 5h ago
   Main PID: 1822 (nginx)
      Tasks: 3 (limit: 4617)
     Memory: 5.8M
        CPU: 612ms

$ sudo systemctl stop nginx
$ sudo systemctl start nginx
$ sudo systemctl restart nginx
```

`enabled` in that status output means the service is set to start automatically at boot — that's a separate flag from whether it's running *right now*:

```bash
$ sudo systemctl enable nginx
Created symlink /etc/systemd/system/multi-user.target.wants/nginx.service → /lib/systemd/system/nginx.service.

$ sudo systemctl disable nginx
```

A service that's `enabled` but not currently `active` will come up on the next reboot; a service that's `active` but not `enabled` is running right now but won't survive a reboot — a very common cause of "it worked yesterday, then the server rebooted and the app was just gone."

For logs, forget hunting through `/var/log` by hand — ask `journalctl` directly, scoped to the unit:

```bash
$ sudo journalctl -u nginx --since "10 min ago"
Oct 02 14:55:03 web-01 nginx[1823]: 10.0.0.9 - - "GET /health HTTP/1.1" 200 2
Oct 02 14:55:12 web-01 nginx[1823]: 10.0.0.9 - - "GET /api/users HTTP/1.1" 500 128

$ sudo journalctl -u nginx -f
-- Following journal, Ctrl+C to exit --
```

`-f` follows the log live, exactly like `tail -f`, which is what you want open in a terminal while you reproduce a bug or watch a deploy roll out.

## Exercise

You're handed a flaky internal tool: a bash script at `/opt/reporting/run.sh` that's supposed to run as a systemd service called `reporting.service`, owned by a dedicated `reportuser` account, logging its output somewhere you can inspect with `journalctl`. Right now none of that exists. Your job:

1. Create the `reportuser` system account and the script at `/opt/reporting/run.sh` (even a one-line `echo "report ran at $(date)"` loop is fine).
2. Set ownership and permissions on the script so `reportuser` can execute it but a different, unprivileged user cannot even read it.
3. Write a minimal systemd unit file for it, enable it, start it, and confirm with `systemctl status` that it's both `active` and `enabled`.
4. Use `journalctl -u reporting` to prove it's actually producing output.

**Hint:** a systemd unit file needs at minimum a `[Unit]`, `[Service]` (with `ExecStart` pointing at your script, and `User=reportuser`), and `[Install]` section with `WantedBy=multi-user.target`; it goes in `/etc/systemd/system/reporting.service`, and after creating or editing any unit file you must run `sudo systemctl daemon-reload` before systemd will see it.
