## Building On Git Fundamentals: From "Don't Commit It" To "What Do You Do Instead"

Git Fundamentals gave you a `.gitignore` for infrastructure repos and one blunt instruction buried in a list of file patterns: if a secret ever hits a commit, "treat it as a security incident: rotate the credential, then deal with the git history." That sentence was a pointer forward. This module is the destination: why that's the *entire* remediation plan (not step one of a longer one), what you should be using instead of bare environment variables for anything that matters in production, and how to structure app config so you stop having this problem at all.

## The Plain Environment Variable: What It Actually Gives You

Here's a typical local setup. A `.env` file:

```bash
DATABASE_PASSWORD=Sup3rS3cr3t!
STRIPE_API_KEY=sk_live_51HcAbC123xyz
PORT=3000
```

Loaded by `docker-compose.yml`:

```yaml
services:
  app:
    build: .
    env_file:
      - .env
    ports:
      - "3000:3000"
```

And read in the app with `process.env.DATABASE_PASSWORD`. This works. It also means the plaintext secret now lives in the process's environment block for as long as the process runs, which is readable by more things than you'd expect. On the host running that container:

```bash
$ docker inspect app-container --format '{{.Config.Env}}'
[DATABASE_PASSWORD=Sup3rS3cr3t! STRIPE_API_KEY=sk_live_51HcAbC123xyz PORT=3000]
```

Or directly through the kernel, for any process you have permission to inspect:

```bash
$ ps eww -p 4821
  PID COMMAND
 4821 node server.js DATABASE_PASSWORD=Sup3rS3cr3t! STRIPE_API_KEY=sk_live_51HcAbC123xyz PORT=3000

$ cat /proc/4821/environ | tr '\0' '\n'
DATABASE_PASSWORD=Sup3rS3cr3t!
STRIPE_API_KEY=sk_live_51HcAbC123xyz
PORT=3000
```

And in CI: GitHub Actions masks a value in logs **only** if it was registered as an Actions secret and referenced via `${{ secrets.X }}`. A value sourced from a committed `.env` file or echoed by a debug step is not masked at all:

```yaml
- name: debug env (do not do this)
  run: env
```

```text
DATABASE_PASSWORD=Sup3rS3cr3t!
STRIPE_API_KEY=sk_live_51HcAbC123xyz
```

That log is visible to anyone with read access to the repo, and on a public repo, to anyone at all, for as long as the workflow run is retained. None of this is a bug in `ps`, Docker, or Actions — it's what an environment variable *is*: a string sitting in a block of memory that the OS and anything with process-inspection rights can read.

## What A Real Secrets Manager Adds

A secrets manager (AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault) doesn't change the fact that your running app eventually needs the plaintext value in memory. What it changes is everything around that: how the value gets there, who's allowed to ask for it, whether asking is recorded, and how hard it is to change the value everywhere it's used.

Fetched at runtime, directly into application memory, never as an OS environment variable:

```python
import boto3, json

client = boto3.client("secretsmanager", region_name="us-east-1")
response = client.get_secret_value(SecretId="prod/myapp/database-password")
db_password = json.loads(response["SecretString"])["password"]

# db_password is a local Python variable. It was never set via
# os.environ, so none of these expose it:
#   ps eww -p <pid>
#   cat /proc/<pid>/environ
#   docker inspect <container>
#   an accidental `env` dump in a CI log
```

Access is scoped and recorded. The IAM policy that lets a role call `GetSecretValue` on exactly this secret:

```hcl
resource "aws_iam_role_policy" "ecs_task_read_secret" {
  name = "read-db-password"
  role = aws_iam_role.ecs_task_role.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = "secretsmanager:GetSecretValue"
      Resource = aws_secretsmanager_secret.db_password.arn
    }]
  })
}
```

...and every single call against that secret shows up in CloudTrail, with who made it and when:

```json
{
  "eventName": "GetSecretValue",
  "eventTime": "2026-10-03T14:02:11Z",
  "userIdentity": {
    "arn": "arn:aws:sts::123456789012:assumed-role/ecs-task-role/myapp-task-8f3a"
  },
  "requestParameters": { "secretId": "prod/myapp/database-password" }
}
```

A `.env` file gives you none of that — no record of who read it, because "reading" it is just opening a file or running `ps`.

Rotation is the other half. With a bare env var, rotating the database password means: generate a new one, find every place the old one is typed (CI secret store, every server's `.env`, maybe a teammate's laptop), update all of them, restart every service, hope you didn't miss one. With Secrets Manager, rotation is a scheduled Lambda that rotates the credential at the database and writes the new value to the secret:

```bash
aws secretsmanager rotate-secret \
  --secret-id prod/myapp/database-password \
  --rotation-lambda-arn arn:aws:lambda:us-east-1:123456789012:function:SecretsManagerRDSPostgresRotation \
  --rotation-rules AutomaticallyAfterDays=30
```

Every service that fetches the secret at startup (rather than baking it into a build) picks up the new value on its next restart, automatically, with zero human touching a config file.

| | Plain env var (`.env` / CI secret) | Cloud secrets manager |
|---|---|---|
| Rotation | Manual, everywhere it's set | One scheduled job; fetched fresh at runtime |
| Access auditing | None | Every `GetSecretValue` logged: who, when |
| Process/CI visibility | Lives in the OS env block — `ps`, `/proc/pid/environ`, `docker inspect`, CI `env` dumps all expose it | Fetched into app memory via an authenticated API call, never set as an env var |
| At rest | Plaintext in a file, CI store, or image layer | Encrypted; decrypted only on authorized retrieval |

A GitHub Actions `secrets.*` value sits in between: masked in logs and encrypted at rest in GitHub's store, but it still gets injected as a plain environment variable on the runner for the job's duration (same `ps`/`/proc` exposure on that box), and it has no rotation or per-call audit trail. It's safer than a `.env` committed to the repo. It is not a secrets manager.

## Why Committing A `.env` File Is A Security Incident

Walk through exactly what happens. A developer clones `platform-infra` before `.env` was added to `.gitignore`, runs `git add .`, and pushes:

```bash
$ git add .
$ git commit -m "add local env config"
$ git push origin main
```

Commit `4b8f2c1` now exists on `origin/main`, containing the real `DATABASE_PASSWORD` and `STRIPE_API_KEY` from above. If the repo is public, GitHub's secret-scanning partner program is actively grepping every push for recognizable key formats (`AKIA...`, `sk_live_...`, and dozens more) — for some providers (AWS among them) a valid-looking key on a public repo gets flagged and the provider notified within minutes, often faster than a human reviews the diff. Scanners not affiliated with GitHub are doing the same thing against the public events firehose. The realistic worst case for a leaked cloud key is new EC2 instances appearing in the account within hours, mining crypto on someone else's bill.

Someone notices and "fixes" it:

```bash
$ git rm .env
$ git commit -m "remove .env, oops"
$ git push origin main
```

This fixes nothing. The blob is still reachable:

```bash
$ git log --all --oneline -- .env
e71a09c remove .env, oops
4b8f2c1 add local env config

$ git show 4b8f2c1:.env
DATABASE_PASSWORD=Sup3rS3cr3t!
STRIPE_API_KEY=sk_live_51HcAbC123xyz
```

Pushing a removal commit adds a *new* commit; it doesn't delete the old one. `4b8f2c1` is still on the remote, still fetchable by hash, still inside anyone's clone or fork made before the "fix." Even rewriting history with `git filter-repo` or BFG after the fact doesn't reach copies that already exist elsewhere — and it does nothing retroactively about whoever already scraped the value in the minutes between push and cleanup.

That's why the remediation order is fixed, and step one is never `git rm`:

1. **Rotate the credential at the provider immediately** — new database password, revoked-and-reissued API key. The leak happened at the push, not at discovery; you cannot know whether it was scraped, and scraping costs an attacker nothing.
2. **Audit what the credential could reach** — check CloudTrail/billing for anything unexpected in the window since the push.
3. **Clean the git history** (`git filter-repo`, BFG) — hygiene, done after, because it does not undo the exposure.

A deleted commit is not an unrotated-but-safe commit. Treat exposure as compromise the moment it's pushed.

## 12-Factor Config: Config In The Environment

The 12-factor app's third principle is "store config in the environment" — meaning environment variables, not files baked into the codebase, and strict separation between code and the values that differ per deploy. Hardcoded, wrong:

```python
# config.py — WRONG: ties this build to one environment, and
# the secret is now in source control forever.
DATABASE_URL = "postgresql://admin:Sup3rS3cr3t!@prod-db.cluster-xyz.rds.amazonaws.com:5432/app"
STRIPE_API_KEY = "sk_live_51HcAbC123xyz"
```

To point this at staging, someone edits the file and commits — which is exactly how secrets end up in git history in the first place. Externalized correctly:

```python
# config.py — CORRECT: no secret values exist in this file at all.
import os

def require_env(name):
    value = os.environ.get(name)
    if value is None:
        raise RuntimeError(f"Missing required environment variable: {name}")
    return value

DATABASE_URL = require_env("DATABASE_URL")
STRIPE_API_KEY = require_env("STRIPE_API_KEY")
```

Now one built image runs unchanged across every environment — only what's injected at run time differs:

```bash
# dev
docker run -e DATABASE_URL="postgresql://dev:dev@localhost:5432/app" -e STRIPE_API_KEY="sk_test_abc" myapp:1.4.0

# staging
docker run -e DATABASE_URL="postgresql://app:***@staging-db.internal:5432/app" -e STRIPE_API_KEY="sk_test_xyz" myapp:1.4.0

# prod — values come from the secrets manager at deploy time, never typed on a command line
```

The Dockerfile backs this up by never setting config in a layer:

```dockerfile
FROM node:20-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
# No ENV lines for DATABASE_URL or any API key — this image is
# identical in dev, staging, and prod.
EXPOSE 3000
CMD ["node", "server.js"]
```

Compare to `ENV DATABASE_URL=postgresql://admin:Sup3rS3cr3t!@prod-db...` baked into a Dockerfile: that value sits in an image layer forever, visible to `docker history` on anyone who pulls the image, and the image itself becomes environment-specific — the opposite of 12-factor's build/release/run separation.

For local dev, commit a placeholder and gitignore the real file — the same pattern Git Fundamentals already told you to apply:

```bash
# .env.example — committed, documents what's needed, no real values
DATABASE_URL=postgresql://user:password@localhost:5432/app
STRIPE_API_KEY=sk_test_replace_me
```

```text
# .gitignore
.env
```

## Exercise

You've inherited `platform-infra`. `main` has no `.env` file today, but `git log --all` shows one was added three commits ago and removed one commit later. Nobody mentioned rotating anything.

1. Find the commit(s) that touched `.env` without already knowing their messages — use `git log --all -- .env`, or the `-S` pickaxe on a string you'd expect inside it (a variable name) if the path itself is ambiguous.
2. Extract the leaked plaintext with `git show <commit>:.env`.
3. Write the remediation steps in the correct order, and justify why step one can't be deleting the file from history.
4. Refactor the app's config loading using the `require_env` pattern above so a secret with a hardcoded fallback can't ship again.

**Hint:** rotation and history cleanup are independent tasks — only one of them is time-sensitive, and it doesn't wait on the other.
