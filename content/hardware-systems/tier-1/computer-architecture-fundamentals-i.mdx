## Von Neumann, One Level Deeper: The Stored-Program Idea

Tier 0 gave you the wiring-diagram version of von Neumann vs. Harvard: one shared bus carrying both instructions and data, versus two separate buses. That's true, but it's not the *interesting* part. The interesting part is what sharing one memory for both instructions and data actually buys you: the **stored-program** idea.

Before stored-program machines, "reprogramming" a computer meant physically rewiring it. ENIAC (1945) was reprogrammed by re-plugging cables and resetting switches — a job that could take days. The stored-program insight, formalized in the 1945 EDVAC report von Neumann's name is attached to, is that a program's instructions can be encoded as numbers and sit in the *same* memory as the data those instructions operate on. To run a different program, you don't touch a single wire — you load different bits into RAM. Your laptop opening a browser one minute and a compiler the next is this idea, unchanged, eighty years later.

This has a sharp consequence: at the level of raw bits in RAM, there is nothing that distinguishes an instruction from a piece of data. The byte `0x05` might be the number five sitting in an array, or it might be an opcode telling the CPU to add two registers. The *only* thing that decides which is which is how the CPU is currently using that address — is the program counter pointing at it (instruction), or did an instruction's operand field point at it (data)? Mixing these up on purpose is exactly how a buffer-overflow exploit works; mixing them up by accident is exactly why "code" and "data" segments get marked with different memory permissions in a real OS. That's a Tier 3 topic, but the reason it's even possible traces straight back to this one architectural choice.

The five classical von Neumann components are: a **memory unit** (holds both instructions and data), an **arithmetic/logic unit**, a **control unit**, and **input/output**, all connected by a shared bus. Today, "CPU" is the name for the control unit, the ALU, and a register file packaged together on one chip. The rest of this module walks through each of those CPU-internal pieces, then the bus that ties everything together.

## The ALU: What It Actually Computes

The arithmetic/logic unit does exactly what its name says and nothing else — it's a pure combinational circuit with no memory of its own. Feed it two operands and a control signal, and it produces one output. Change the control signal, and the *same* two operands produce a different output on the very next cycle.

Recall the full adder from Boolean Algebra & Combinational Logic: it takes inputs A, B, and a carry-in, and produces a Sum and a carry-out. Chain four of them together, each carry-out feeding the next carry-in, and you get a 4-bit ripple-carry adder. That adder isn't a separate component sitting next to the ALU — **it is the ALU's ADD circuit.** The ALU wraps that adder together with an AND gate array, an OR gate array, some inverters, and a multiplexer that picks which one's output actually reaches the ALU's output pins, based on a control signal coming from the control unit.

Here's a 4-function, 4-bit ALU, control-bit by control-bit:

```
 A[3:0] ──┬──────────┬──────────┬──────────┐
 B[3:0] ──┤          │          │          │
          AND        OR       ADDER     ADDER+invertB
          gates      gates   (Cin=0)      (Cin=1)
           │          │          │          │
           └────┬─────┴────┬─────┴────┬─────┘
                │          │          │
              4-to-1 MUX, selected by control[1:0]
                        │
                    Result[3:0]
```

Control = `00` selects AND, `01` selects OR, `10` selects the adder with B unmodified and Cin=0 (ADD), `11` selects the adder with B inverted and Cin=1 (SUBTRACT — this is exactly the two's-complement "invert and add 1" trick from Tier 0, wired into hardware instead of done by hand). As pseudocode, the mux's job looks like this:

```c
switch (alu_control) {          // 2 bits, set by the control unit's decoder
    case 0b00: result = A & B;                     break; // AND
    case 0b01: result = A | B;                     break; // OR
    case 0b10: result = ripple_add(A,  B, /*Cin*/0); break; // ADD
    case 0b11: result = ripple_add(A, ~B, /*Cin*/1); break; // SUB
}
zero_flag = (result == 0b0000);
```

Worked ADD: control=`10`, A=`0110` (6), B=`0101` (5), Cin=0. The 4-bit ripple-carry adder produces Sum=`1011` (11) and carry-out=0 (6+5=11 fits in 4 bits, so nothing overflows).

Worked SUBTRACT: control=`11`, A=`0111` (7), B=`0011` (3). The ALU inverts B to `1100`, then adds A + ~B + Cin(1): `0111 + 1100 + 1 = 10100`. Keep only the low 4 bits: `0100` (4). 7 − 3 = 4 — correct, and it cost the hardware nothing but an extra set of inverters on B's input and a hardwired Cin=1, because addition circuitry it already had does the rest. This is precisely the 8-bit ALU (ADD, SUB, AND, OR, NOT, zero flag) you'll build gate-by-gate in this tier's checkpoint project — same idea, twice the bit width, two more operations.

## The Control Unit and Fetch-Decode-Execute

If the ALU is the muscle, the control unit is the part reading the instructions and pulling the levers. Its job, every single cycle, is the same three-step loop:

1. **Fetch.** The **program counter (PC)** register holds the memory address of the next instruction. That address goes out on the address bus; the control unit asserts a read signal on the control bus; the instruction bits that come back on the data bus get latched into the **instruction register (IR)**.
2. **Decode.** The control unit splits the IR's bits into fields — typically an opcode field and one or more register/operand fields — and turns the opcode into the actual control signals: which 2-bit code to send the ALU, which registers to read, whether this instruction reads or writes memory.
3. **Execute.** The ALU computes (or a memory read/write happens, or a register is loaded), and the result lands where the decoded fields say it should — a register, a memory address, or the PC itself in the case of a jump.

Then the PC updates — usually +1 instruction, or a completely new value if the instruction just executed was a jump — and the loop repeats. This is a structural account, not a timing-accurate one; the next module (Sequential Logic & the Fetch-Decode-Execute Cycle) covers the actual flip-flops and clock edges that make the PC, IR, and registers hold their values between cycles.

Notice what fetch and execute have in common in a von Neumann machine: they can both need the *same* bus in the *same* instruction cycle — fetch to grab the instruction, execute to grab a data operand from memory. Only one of those can use the bus at a time. That collision is the literal "von Neumann bottleneck" Tier 0 named without fully explaining — now you can see exactly which two steps are fighting over the same road.

## The Register File: Fast Storage the CPU Can't Live Without

RAM is fast compared to a disk, but it is not fast compared to the CPU sitting next to it. A modern CPU can execute an instruction roughly every clock cycle; a round trip out to RAM takes 50-100+ cycles. If every ALU operation had to read both its operands from RAM and write its result back to RAM, the CPU would spend the overwhelming majority of its time waiting, not computing.

The fix is the **register file**: a small block of storage built from the same fast logic as the rest of the CPU, sitting directly on the chip, readable and writable in about one clock cycle — no bus trip required. An x86-64 chip exposes 16 general-purpose 64-bit registers (`RAX` through `R15`); ARM64 exposes 31 (`X0`-`X30`). A register file needs at least two read ports (most ALU operations need two operands at once) and at least one write port, all addressed directly by a few bits pulled straight out of the instruction — a 4-bit field can select any one of 16 registers, no lookup needed.

Do the arithmetic on size: 16 registers × 8 bytes each is 128 bytes of storage, next to gigabytes of RAM. The register file is minuscule on purpose — it isn't there to hold much, it's there to hold *whatever the ALU needs right now* at a speed RAM structurally cannot match.

## The Memory Hierarchy: Real Numbers

Every level below the register file trades speed for capacity, and the gaps are enormous — not 2x or 3x, but often one to five orders of magnitude:

| Level | Typical latency | Typical size |
|---|---|---|
| Registers | well under 1 ns | ~100-1,000 bytes |
| L1 cache | ~1 ns | 32-64 KB per core |
| L2 cache | ~3-10 ns | 256 KB-1 MB per core |
| L3 cache | ~10-20 ns | 8-32 MB, shared across cores |
| RAM (DRAM) | ~70-100 ns | 8-64 GB |
| NVMe SSD | ~50-150 microseconds | 250 GB-4 TB |
| HDD | ~5-10 milliseconds | 1-16 TB |

Stretch the numbers to a human timescale to feel the actual gap: if one register access took 1 second, an L1 hit would take a few seconds, a RAM access would take about a minute and a half, an SSD access would take almost a week, and a spinning hard drive seek would take over a year. That's not exaggeration for effect — it's the same ratio, just scaled up from nanoseconds to seconds. It's also the entire reason caching exists at every level of software, from CPU cache lines to your browser caching images: reaching one level down the hierarchy is expensive enough to be worth avoiding whenever the data you need was already used recently.

## Buses: Three Distinct Roads, Not One

"The bus" is really three separate, simultaneously-active buses doing three different jobs:

- **Address bus** — carries *where*. The CPU drives a memory address onto it. It's one-directional (CPU to memory/devices), and its width caps how much memory can ever be directly addressed: a 16-line address bus can express 2¹⁶ = 65,536 distinct addresses — 64 KB, full stop, no matter how much RAM is physically installed.
- **Data bus** — carries *what*. The actual bits being transferred ride here. It's bidirectional — the CPU drives it during a write, memory drives it during a read — and its width sets how many bytes move per transfer: a 64-bit data bus moves 8 bytes at a time.
- **Control bus** — carries *how and when*. Read/write select lines, a clock signal, interrupt requests, and a "data ready" line all travel here, coordinating the other two buses so the CPU and memory agree on the exact moment a transfer is valid.

Concretely, trace a single memory read of the byte at address `0x1000`: the CPU drives `0000000000001000` (0x1000 as 16 bits) onto the address bus, asserts READ on the control bus, and waits. Main memory decodes that address, drives the requested byte's bits onto the data bus, and asserts READY on the control bus once that data is valid. The CPU only latches whatever is on the data bus into a register the instant it sees READY — without the control bus, the CPU would have no way to know whether the data bus currently holds real data or garbage left over from the previous transfer.

## Exercise: Trace a Load Instruction by Hand

You have a small von Neumann machine: an 8-bit data bus, a 12-bit address bus, and the 4-function ALU described above (control bits `00`=AND, `01`=OR, `10`=ADD, `11`=SUB). The PC currently holds `0x050`. At that address sits a `LOAD` instruction whose operand field encodes the address `0x0C4`, and the byte stored at `0x0C4` is `00010111`.

Write out, step by step, every value that appears on the address bus, the data bus, and the control bus during (a) the fetch of the `LOAD` instruction itself and (b) the subsequent memory access the instruction triggers to actually retrieve the byte at `0x0C4`. Then, separately: if that retrieved byte were fed into the ALU as operand A along with B = `00001001` and control = `11`, what 8-bit result and what interpretation (as a signed two's-complement number) comes out?

*Hint:* there are two completely separate address-bus/data-bus/control-bus cycles here, not one — the first moves the instruction itself from memory into the IR, and only *after* decoding does the second cycle happen to fetch the operand the instruction pointed to. Keep the two cycles in two separate tables so you don't accidentally merge them. For the ALU part, subtraction is addition with B inverted and Cin=1 — work it exactly like the 7−3 example above, one bit column at a time.
