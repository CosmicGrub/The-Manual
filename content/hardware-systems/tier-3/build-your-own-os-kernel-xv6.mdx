## The xv6-riscv source tree: what each file actually owns

You're going to work in `github.com/mit-pdos/xv6-riscv` directly, so the first job is a map, not a summary. Clone it and build before reading further:

```bash
git clone https://github.com/mit-pdos/xv6-riscv.git
cd xv6-riscv
make
```

This needs a RISC-V cross toolchain (`riscv64-unknown-elf-gcc` or `riscv64-linux-gnu-gcc`) and `qemu-system-riscv64`. If `make` finds them, it produces `kernel/kernel` (an ELF with full debug symbols — you'll want those for GDB later) and `fs.img` (the root filesystem image, built by the host-side `mkfs` tool from `mkfs/mkfs.c`).

The kernel is about 25 files. Here are the ones that own the mechanisms you'll actually touch:

| File | Owns |
|---|---|
| `kernel/proc.c` / `proc.h` | The process table (`struct proc proc[NPROC]`, `NPROC=64`), `allocproc()`/`freeproc()`, `fork()`, `exit()`, `wait()`, the per-CPU `scheduler()` loop, `sleep()`/`wakeup()`, `yield()`, `kill()`. |
| `kernel/trap.c` | `usertrap()`/`usertrapret()` (user↔kernel transitions), `kerneltrap()` (traps while already in supervisor mode — timer ticks, device IRQs during kernel code), `devintr()`. |
| `kernel/vm.c` | Page tables: `walk()` (walks a `pagetable_t` to find or create a PTE), `walkaddr()`, `mappages()`, `uvmcreate()`, `uvmalloc()`/`uvmdealloc()`, `uvmcopy()` (fork's full address-space duplication — no copy-on-write in base xv6), `copyout()`/`copyin()`/`copyinstr()`. |
| `kernel/fs.c` | On-disk layout: superblock, inode blocks, free-block bitmap, data blocks. `balloc()`/`bfree()`, `ialloc()`/`iget()`/`ilock()`, `bmap()` (logical block number inside an inode → disk block number, via direct pointers plus one indirect block), `readi()`/`writei()`, `dirlookup()`/`dirlink()`, `namei()`. |
| `kernel/syscall.c` | The dispatch table `syscalls[]` and argument fetchers `argint()`/`argaddr()`/`argstr()`/`fetchstr()`. |
| `kernel/sysproc.c`, `kernel/sysfile.c` | The actual `sys_*` implementations — process-related ones in the former, file/fd-related ones in the latter. |
| `kernel/trampoline.S`, `kernel/kernelvec.S` | The hand-written assembly that actually crosses the user/kernel boundary (`uservec`/`userret`) and handles traps that arrive while the kernel itself is running. |
| `kernel/exec.c` | ELF loading for `exec()`. |
| `kernel/file.c`, `kernel/pipe.c`, `kernel/log.c`, `kernel/bio.c` | The fd layer (`struct file`), pipes, the write-ahead log for crash consistency, and the block buffer cache. |
| `kernel/kalloc.c` | The physical page allocator (a simple free list over `end` to `PHYSTOP`). |

The call chain for a file write looks like `sys_write` (sysfile.c) → `filewrite` (file.c) → `writei` (fs.c) → `log_write`/`bwrite` (log.c/bio.c) → `virtio_disk_rw` (virtio_disk.c). Knowing that chain is what lets you find "where does X actually happen" without grepping blindly.

## Tracing getpid() end to end

`getpid` is the simplest syscall in xv6 because it touches no arguments and no memory — it's pure control flow, which makes it the cleanest trace.

**1. The user-space stub.** `user/user.h` declares `int getpid(void);`. The implementation isn't C — it's generated by `user/usys.pl` into `user/usys.S`:

```asm
.global getpid
getpid:
 li a7, SYS_getpid
 ecall
 ret
```

`SYS_getpid` is `11`, defined in `kernel/syscall.h` alongside the other twenty-one syscall numbers (`SYS_fork=1` through `SYS_close=21`). Loading it into `a7` and executing `ecall` is the entire user-side cost of a syscall: one register load, one trap instruction.

**2. The trap.** `ecall` from user mode sets `scause=8`, sets `sepc` to the address of the `ecall` instruction itself, and jumps to whatever address is in `stvec`. While running user code, `stvec` points at `uservec` inside the trampoline page — a page mapped at the identical virtual address (`TRAMPOLINE`, just below the top of the address space) in *every* page table, user and kernel alike, so the instruction pointer stays valid across the page-table switch that's about to happen. `uservec` (abridged — the real file saves all 31 integer registers the same way):

```asm
.globl uservec
uservec:
    csrrw a0, sscratch, a0   # a0 <-> sscratch: a0 now points at the trapframe
    sd ra, 40(a0)
    sd sp, 48(a0)
    sd gp, 56(a0)
    sd a7, 168(a0)           # the syscall number, now safe in the trapframe
    # ... all other GPRs ...
    ld t0, 16(a0)            # trapframe->kernel_trap  (== usertrap)
    ld t1, 0(a0)             # trapframe->kernel_satp
    ld sp, 8(a0)             # trapframe->kernel_sp
    csrw satp, t1
    sfence.vma zero, zero
    jr t0                    # off to usertrap()
```

The trapframe is a fixed-layout struct (`kernel/proc.h`) that `trampoline.S` indexes by raw byte offset, so the two files must stay in lockstep — comments in both name the offsets for exactly this reason.

**3. `usertrap()`** (`kernel/trap.c`), abridged:

```c
void usertrap(void) {
  struct proc *p = myproc();
  w_stvec((uint64)kernelvec);        // traps from here on go to kerneltrap
  p->trapframe->epc = r_sepc();

  if (r_scause() == 8) {             // syscall
    if (p->killed) exit(-1);
    p->trapframe->epc += 4;          // skip past the ecall on return
    intr_on();
    syscall();
  } else if ((which_dev = devintr()) != 0) {
    // device interrupt while in user mode, handled
  } else {
    p->killed = 1;                   // unexpected trap
  }
  if (p->killed) exit(-1);
  usertrapret();
}
```

The `epc += 4` matters: without it, returning to user mode would re-execute the same `ecall` forever.

**4. `syscall()`** (`kernel/syscall.c`):

```c
void syscall(void) {
  struct proc *p = myproc();
  int num = p->trapframe->a7;
  if (num > 0 && num < NELEM(syscalls) && syscalls[num]) {
    p->trapframe->a0 = syscalls[num]();   // return value goes where a0 is restored from
  } else {
    p->trapframe->a0 = -1;
  }
}
```

`syscalls[]` is an array of function pointers indexed by syscall number, with `[SYS_getpid] sys_getpid` among its twenty-one entries.

**5. `sys_getpid()`** (`kernel/sysproc.c`) — the entire kernel-side payload:

```c
uint64 sys_getpid(void) {
  return myproc()->pid;
}
```

`myproc()` reads `cpus[cpuid()].proc`; `pid` was stamped once in `allocproc()` from a monotonically increasing counter protected by `pid_lock`. No locking is needed here because a process only ever reads its own `pid`.

**6. The return path.** `syscall()` wrote the pid into `p->trapframe->a0`. `usertrapret()` restores `stvec` to point at `uservec` again, saves kernel context into the trapframe (`kernel_satp`, `kernel_sp`, `kernel_trap`), sets `sepc` from `p->trapframe->epc`, and calls `userret` — in the trampoline page — with the user `satp` value as its argument. `userret` switches `satp` back to the user page table, then reloads every register from the trapframe *except* `a0`, which it loads last (since `a0` is the pointer to the trapframe itself until that point), then executes `sret`. Control resumes at the instruction after `ecall` in the `getpid` stub — the `ret` — with `a0` holding the pid. That's the whole round trip.

## Worked example: adding `getreadcount()`

Say you want a syscall that returns how many times the calling process has called `read()`. This touches every layer you just traced, which is exactly why it's the standard way to learn the plumbing. Six files change:

**`kernel/proc.h`** — add a field to `struct proc`:

```c
struct proc {
  ...
  int nread;              // number of read() calls made by this process
};
```

**`kernel/syscall.h`** — the next free number after `SYS_close` (21):

```c
#define SYS_getreadcount 22
```

**`user/usys.pl`** — append a generator call so `make` regenerates `usys.S`:

```perl
entry("getreadcount");
```

**`user/user.h`** — declare it for C callers:

```c
int getreadcount(void);
```

**`kernel/sysproc.c`** — the implementation:

```c
uint64
sys_getreadcount(void)
{
  return myproc()->nread;
}
```

**`kernel/syscall.c`** — wire it into the dispatch table:

```c
extern uint64 sys_getreadcount(void);
...
static uint64 (*syscalls[])(void) = {
  ...
  [SYS_close]        sys_close,
  [SYS_getreadcount] sys_getreadcount,
};
```

**`kernel/sysfile.c`** — increment the counter where `read()` actually lands:

```c
uint64
sys_read(void)
{
  struct file *f;
  int n;
  uint64 p;

  argaddr(1, &p);
  argint(2, &n);
  if (argfd(0, 0, &f) < 0)
    return -1;
  myproc()->nread++;        // added
  return fileread(f, p, n);
}
```

Run `make qemu`, and from the xv6 shell you can now write a tiny `user/readtest.c` (add `$U/_readtest\` to `UPROGS` in the Makefile) that calls `read()` a few times and prints `getreadcount()` to confirm it tracks. Notice the shape: a new syscall is never one function, it's a number, a stub, a dispatch-table entry, and the state it actually reads or mutates — here, one `int` on `struct proc`.

## Booting under QEMU with GDB attached

```bash
make qemu-gdb
```

This builds normally, then launches QEMU with `-S` (CPU halted at reset — nothing executes until a debugger tells it to) and `-gdb tcp::<port>`, where `<port>` is derived from your UID (`25000 + uid % 5000`) so multiple people on a shared machine don't collide. QEMU prints:

```
*** Now run 'gdb' in another window.
```

and waits. In a second terminal, from the same `xv6-riscv` directory:

```bash
gdb-multiarch kernel/kernel
```

(or `riscv64-unknown-elf-gdb kernel/kernel` if you have the cross-gdb). The repo's `Makefile` generates a `.gdbinit` from `.gdbinit.tmpl-riscv` with the right port substituted in, which sets the architecture and issues `target remote localhost:<port>` automatically — *if* GDB is allowed to auto-load it. Modern GDB refuses to source a local `.gdbinit` by default; add one line to `~/.gdbinit`:

```
add-auto-load-safe-path /full/path/to/xv6-riscv/.gdbinit
```

Now set a breakpoint and let the halted CPU go:

```
(gdb) break syscall
Breakpoint 1 at 0x80002d3e: file kernel/syscall.c, line 133.
(gdb) continue
```

That first `continue` is required even to let the kernel boot, since `-S` started it frozen. The very first syscall to fire is the init process's own `exec("sh", ...)` — `userinit()` builds process 1 directly in the kernel without going through the trap path, so its first syscall happens only once `/init` runs in user mode. You'll land in `syscall()` right there. From the breakpoint:

```
(gdb) print p->trapframe->a7
$1 = 7          # SYS_exec
(gdb) print *p
$2 = {lock = {...}, state = RUNNING, pid = 2, name = "initcode", ...}
(gdb) bt
#0  syscall () at kernel/syscall.c:133
#1  usertrap () at kernel/trap.c:88
#2  0x0000000080007c0a in uservec ()
(gdb) continue
```

Each subsequent `continue` runs until the next `ecall` from any process. Typing a command at the xv6 shell prompt will hit this breakpoint repeatedly — once for the shell's own `fork`, once for its `exec` of the program you typed, and so on — letting you read `p->trapframe->a7` each time to see the syscall sequence a single command line actually generates. To isolate `getpid` specifically, make the breakpoint conditional: `break syscall if p->trapframe->a7 == 11`.

## Exercise

Implement `getppid()`: a syscall returning the calling process's *parent's* pid. Follow the same six-file pattern as `getreadcount()` above — but there's a wrinkle `getreadcount` didn't have. `p->parent` isn't owned by `p->lock`; it's protected by a separate global `wait_lock` in `proc.c`, because `exit()` reparents a dying process's children to `init` while `wait()` on another CPU may be reading that same pointer. Look at how `wait()` itself acquires `wait_lock` before touching `p->parent`, and do the same before you dereference `p->parent->pid` in your `sys_getppid()`. Test it by calling `getppid()` from a child right after `fork()` and checking it matches the parent's `getpid()`.
