## Beyond the First Taste

Tier 3's Go module gave you goroutines and channels as a first taste — `go f()`, an unbuffered channel, maybe a two-stage pipeline. That's assumed here. This module builds the mental model working Go engineers actually use: channel buffering semantics, `select`, the fan-out/fan-in shape, when `sync` beats a channel, how to *prove* a data race instead of guessing, and how to profile a Go program instead of speculating about its hot path.

## Channels, Precisely

### Unbuffered: a rendezvous, not a mailbox

An unbuffered channel has zero capacity. A send blocks until a receiver is ready to take the value *at that instant* — it's a synchronization point, not storage.

```go
func main() {
	ch := make(chan int)
	go func() {
		ch <- 42 // blocks until someone receives
	}()
	fmt.Println(<-ch) // unblocks the sender, prints 42
}
```

If you remove the `go` and just write `ch <- 42; fmt.Println(<-ch)` in `main`, the program deadlocks: the send blocks forever because nothing is receiving concurrently. The runtime detects this and panics with `fatal error: all goroutines are asleep - deadlock!`. This is one of the most common Tier-4-level bugs — treating an unbuffered channel like a queue.

### Buffered: a bounded queue

A buffered channel holds up to N values without a receiver present:

```go
ch := make(chan int, 2)
ch <- 1 // does not block, buffer has room
ch <- 2 // does not block, buffer full
// ch <- 3 // would block here until something receives
fmt.Println(<-ch, <-ch) // 1 2
```

Sends block only once the buffer is full; receives block only once it's empty. Buffering decouples producer and consumer speed *up to the buffer size*, but it does not remove backpressure — it just delays when backpressure kicks in. A common mistake is using a large buffer to "fix" a deadlock without understanding why the deadlock existed; that usually just moves the failure further downstream.

A buffered channel of capacity N doubling as a counting semaphore is a genuinely useful idiom — more on that in the exercise.

### `select`: waiting on multiple channels

`select` blocks until one of its cases can proceed. If several are ready simultaneously, Go picks one uniformly at random — don't rely on case order.

```go
func fetch(url string, out chan<- string) {
	time.Sleep(200 * time.Millisecond)
	out <- url
}

func main() {
	results := make(chan string)
	go fetch("https://example.com", results)

	select {
	case r := <-results:
		fmt.Println("got:", r)
	case <-time.After(100 * time.Millisecond):
		fmt.Println("timed out")
	}
}
```

`time.After` returns a channel that fires once after the duration — this is the standard timeout pattern. Two things to watch for in real code: `time.After` in a hot loop leaks timers until they fire (prefer a reused `time.Timer` if you're calling this thousands of times a second), and a `select` with a `default` case never blocks — it's a poll, not a wait:

```go
select {
case v := <-ch:
	fmt.Println("got", v)
default:
	fmt.Println("nothing ready, moving on")
}
```

The other essential `select` idiom is the cancellation channel, almost always spelled `ctx.Done()` in real code:

```go
func worker(ctx context.Context, jobs <-chan int) {
	for {
		select {
		case <-ctx.Done():
			return
		case j, ok := <-jobs:
			if !ok {
				return // jobs channel closed
			}
			process(j)
		}
	}
}
```

### Fan-out / fan-in

Fan-out: multiple goroutines read from one channel to parallelize work. Fan-in: multiple channels feed one, to merge results.

```go
func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			out <- n
		}
	}()
	return out
}

func square(in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			out <- n * n
		}
	}()
	return out
}

func fanIn(cs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	wg.Add(len(cs))
	for _, c := range cs {
		go func(c <-chan int) {
			defer wg.Done()
			for n := range c {
				out <- n
			}
		}(c)
	}
	go func() {
		wg.Wait()
		close(out) // safe: only ONE goroutine ever closes out
	}()
	return out
}
```

Wire three `square` stages fed from one `gen` to fan a stream of work across three workers, then merge:

```go
in := gen(1, 2, 3, 4, 5, 6)
c1, c2, c3 := square(in), square(in), square(in)
for v := range fanIn(c1, c2, c3) {
	fmt.Println(v)
}
```

Multiple goroutines safely reading from the same `in` channel is fine — channels are safe for concurrent send/receive by design. The dangerous part is closing: exactly one goroutine may close a channel, and it must only do so after no more sends will happen on it. `fanIn` above gets this right by having a dedicated goroutine wait on a `WaitGroup` before closing `out`. Closing a channel that another goroutine might still send on, or closing it twice, panics at runtime — this is a frequent "spot the bug" in code review.

## Sync Primitives: When to Skip the Channel

Go's proverb — "don't communicate by sharing memory, share memory by communicating" — is a default, not a law. For simple shared state touched by many goroutines, `sync.Mutex` is often clearer and faster than routing everything through a channel and an owning goroutine.

### Mutex and RWMutex

```go
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
```

For read-heavy shared state, `sync.RWMutex` lets any number of readers proceed concurrently, serializing only writers:

```go
type Cache struct {
	mu   sync.RWMutex
	data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.data[key]
	return v, ok
}

func (c *Cache) Set(key, value string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[key] = value
}
```

### WaitGroup — and its classic footgun

`WaitGroup` coordinates "wait until N things finish." The bug that catches almost everyone once:

```go
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
	go func() {
		wg.Add(1) // WRONG: races with Wait() below
		defer wg.Done()
		doWork()
	}()
}
wg.Wait()
```

`wg.Add(1)` runs *inside* the new goroutine, which the scheduler may not run before `main` reaches `wg.Wait()`. If the counter is still zero when `Wait()` is called, `Wait()` returns immediately — before any work has even started. The fix is to call `Add` in the loop that launches the goroutine, before `go` runs:

```go
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		doWork()
	}()
}
wg.Wait()
```

### sync/atomic

For a single counter or flag, atomic operations avoid lock overhead entirely by using CPU-level atomic instructions:

```go
var n int64
var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		atomic.AddInt64(&n, 1)
	}()
}
wg.Wait()
fmt.Println(atomic.LoadInt64(&n)) // 1000
```

Since Go 1.19 there are typed wrappers (`atomic.Int64`, `atomic.Bool`, `atomic.Value`, …) that prevent accidentally mixing atomic and non-atomic access to the same variable — prefer them in new code: `var n atomic.Int64; n.Add(1)`.

**Rule of thumb:** a single counter or flag → atomic. A handful of related fields that must change together → mutex. Ownership of a value passing between stages, or "notify me when this is done" → channel. If you find yourself locking a mutex just to read a channel's state, or sending single primitive values through a channel purely to increment a shared counter, you've picked the wrong tool.

## The Race Detector: Don't Guess, Verify

A data race is two goroutines accessing the same memory location concurrently, at least one a write, with no synchronization. It's undefined behavior in Go, not "probably fine" — the compiler is free to produce surprising results.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	counter := 0
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter++ // read-modify-write, not atomic
		}()
	}
	wg.Wait()
	fmt.Println(counter)
}
```

Run normally and this often prints `1000` anyway — races don't reliably manifest as wrong output, which is exactly what makes them dangerous. Run it with the race detector instead:

```
go run -race main.go
```

You'll get a `WARNING: DATA RACE` report naming the exact line, the goroutine stacks for both the conflicting read and write, and whether it was a read or write on each side. Fix it with a mutex or `atomic.AddInt64(&counter, 1)` and rerun — the warning disappears.

The detector instruments every memory access and is not free: expect 5-10x memory overhead and 2-20x slowdown, so it's a testing and CI tool (`go test -race ./...`), not a production flag. Critically, it only flags races that actually happen during the run you executed — it proves the presence of a bug, never its absence. A race hidden behind a rare timing window can pass `-race` a hundred times and still be there.

## pprof: Measure, Don't Guess

### CPU and memory profiles from a benchmark

```go
func BenchmarkConcat(b *testing.B) {
	for i := 0; i < b.N; i++ {
		s := ""
		for j := 0; j < 1000; j++ {
			s += "x" // reallocates on every append
		}
	}
}
```

```
go test -bench=. -cpuprofile=cpu.prof -memprofile=mem.prof
go tool pprof cpu.prof
```

Inside the interactive pprof shell:

```
(pprof) top10
(pprof) list BenchmarkConcat
```

`list` shows source lines annotated with the fraction of samples attributed to each — you'll see essentially all the time sitting on `s += "x"`, because each `+=` allocates a new string and copies. Swap in `strings.Builder`, which grows a backing buffer geometrically instead of reallocating every iteration, and re-profile to confirm the hot line moved.

### Profiling a live service

For long-running programs, import `net/http/pprof` for its side effect of registering profiling handlers:

```go
import (
	"log"
	"net/http"
	_ "net/http/pprof"
)

func main() {
	go func() {
		log.Println(http.ListenAndServe("localhost:6060", nil))
	}()
	runServer() // the real application
}
```

Then, while the service is under load:

```
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30   # CPU, sampled for 30s
go tool pprof http://localhost:6060/debug/pprof/heap                 # current heap allocations
```

`top` ranks functions by self time (CPU profile) or in-use bytes (heap profile); `web` renders a call graph as an SVG if graphviz is installed. For network-bound code — like the scraper below — the CPU profile is often nearly empty; the interesting story is in the heap profile or in goroutine counts (`/debug/pprof/goroutine`), which will tell you if you're leaking goroutines instead of burning CPU.

## Putting It Together: A Concurrent Scraper

This combines a worker pool (fan-out), context-based cancellation, `select`-driven job dispatch, and a `WaitGroup`-guarded fan-in shutdown — the shape of most real concurrent services in Go.

```go
package main

import (
	"context"
	"fmt"
	"io"
	"net/http"
	"sync"
	"time"
)

type result struct {
	url    string
	status int
	err    error
	dur    time.Duration
}

func worker(ctx context.Context, jobs <-chan string, results chan<- result, client *http.Client) {
	for {
		select {
		case <-ctx.Done():
			return
		case url, ok := <-jobs:
			if !ok {
				return
			}
			start := time.Now()
			req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
			if err != nil {
				results <- result{url: url, err: err}
				continue
			}
			resp, err := client.Do(req)
			if err != nil {
				results <- result{url: url, err: err, dur: time.Since(start)}
				continue
			}
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			results <- result{url: url, status: resp.StatusCode, dur: time.Since(start)}
		}
	}
}

func scrape(urls []string, workerCount int) []result {
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()

	jobs := make(chan string)
	results := make(chan result)
	client := &http.Client{Timeout: 10 * time.Second}

	var wg sync.WaitGroup
	for i := 0; i < workerCount; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			worker(ctx, jobs, results, client)
		}()
	}

	go func() {
		defer close(jobs)
		for _, u := range urls {
			select {
			case jobs <- u:
			case <-ctx.Done():
				return
			}
		}
	}()

	go func() {
		wg.Wait()
		close(results)
	}()

	var out []result
	for r := range results {
		out = append(out, r)
	}
	return out
}

func main() {
	urls := []string{
		"https://example.com",
		"https://go.dev",
		"https://httpbin.org/delay/1",
	}
	for _, r := range scrape(urls, 4) {
		if r.err != nil {
			fmt.Printf("%-30s ERROR %v\n", r.url, r.err)
			continue
		}
		fmt.Printf("%-30s %d %v\n", r.url, r.status, r.dur)
	}
}
```

Trace the shutdown carefully — it's the part beginners get wrong: the dispatcher goroutine closes `jobs` once it's sent every URL (or the context expires), which is what causes each worker's `job, ok := <-jobs` to return `ok == false` and return. A separate goroutine waits on the `WaitGroup` for all workers to finish, *then* closes `results` — closing it any earlier would panic a worker mid-send. `workerCount` controls fan-out; the single `results` channel is the fan-in.

## Exercise

Extend the scraper so that:

1. No more than `N` HTTP requests are in flight globally at once, independent of `workerCount` — even if you bump `workerCount` to 50.
2. It tallies response counts per status code in a shared `map[int]int`, correctly guarded against concurrent access.
3. Temporarily remove the guard from step 2, run `go run -race` against it with a list of 20+ URLs, and confirm the detector reports the race — then put the guard back and confirm it's clean.
4. Wire in `net/http/pprof`, point the scraper at 500+ URLs, and use `go tool pprof` to find where time and memory actually go. Decide, from the data, whether adding more workers would help.

Hint for (1): a semaphore in Go is just a buffered channel used for permits, not payloads: `sem := make(chan struct{}, N)`; acquire with `sem <- struct{}{}` before a request and release with `<-sem` after. It composes cleanly with the worker pool above — put the acquire/release inside `worker`, around the `client.Do` call.
